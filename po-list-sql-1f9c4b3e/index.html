The PO list SQL, explained

What GET /v1/purchase-orders actually runs against the database, and why each join and union is there.

The handler is GetPurchaseOrders in api/purchase_orders.go (route wired in api/router.go). A request triggers two round trips, both built at runtime with sqlx.In (which expands the IN (?) lists) and Rebind (which swaps ? for the driver's placeholder). The first is tidy and cheap. The second is where all the size lives, and it is almost entirely one subquery that answers “how many units on this PO have actually been commissioned, per line?”

1. Query 1 — the PO heads small

This is the query that produces the list itself: one row per purchase order, with its ship-to location joined in. Default view is open (open,partial); view=closed swaps in completed; an explicit status= param overrides both. Everything is fenced to the caller's factory via po.production_location.

SELECT po.id, po.status, po.purchase_order_number,
       COALESCE(po.urn, '')                   AS urn,
       COALESCE(po.purchase_order_issuer, '') AS purchase_order_issuer,
       COALESCE(po.supplier, '')              AS supplier,
       COALESCE(l.id, '')                     AS ship_to_id,
       COALESCE(l.location_name, '')          AS ship_to_name,
       COALESCE(DATE_FORMAT(po.purchase_order_date, '%Y-%m-%d'), '') AS purchase_order_date
FROM purchase_order po
LEFT JOIN location l ON po.ship_to_location = l.id
WHERE po.status IN (?)                  -- 'open','partial' by default
  AND po.production_location = ?        -- the caller's factory (the fence)
ORDER BY (po.status = 'partial') DESC,     -- part-done work floats to the top
         po.purchase_order_date DESC,
         po.purchase_order_number
Why a LEFT JOIN? A purchase order that has not been assigned a ship-to location must still appear in the list. An inner join would silently drop it. The COALESCE(..., '') around the joined columns does the same job at the value level: absent becomes an empty string, matching the nested JSON contract the app expects, and turning the missing location into null in the response rather than a phantom object.

2. Query 2 — the line items with activation counts the big one

Once the heads are known, the handler collects their ids and runs this. The outer half is boring: get each PO's lines, and the product behind each line. The whole of the complexity is the LEFT JOIN (…) active_items subquery on the right, which computes qty_activated per PO urn + product.

SELECT poli.purchase_order_id, poli.id AS line_item_id,
       COALESCE(poli.configuration_id, '') AS configuration_id,
       p.id AS product_id, COALESCE(p.product_name, '') AS product_name,
       COALESCE(p.gtin, '') AS gtin, COALESCE(p.size, '') AS size,
       COALESCE(p.variant_description, '') AS variant_description,
       CAST(poli.quantity AS SIGNED) AS qty_ordered,
       COALESCE(active_items.qty_activated, 0) AS qty_activated
FROM purchase_order_line_item poli
JOIN purchase_order po ON po.id = poli.purchase_order_id
JOIN product p ON poli.product = p.id
LEFT JOIN (
  /* ———— the activation-count subquery, see sections 3–5 ———— */
  WITH requested AS (
    SELECT DISTINCT po.urn AS biz_transaction_po_id, poli.product AS product_join_key
    FROM purchase_order_line_item poli
    JOIN purchase_order po ON po.id = poli.purchase_order_id
    WHERE poli.purchase_order_id IN (?)            -- just this page of POs
  ),
  candidate_items AS (
    SELECT DISTINCT COALESCE(NULLIF(c.epc_join_key, ''), c.epc_id_raw) AS item_id
    FROM epc_events p
    JOIN requested r ON r.product_join_key = p.product_join_key
    JOIN epc_events c USE INDEX(epc_events_biz_location_join_key_foreign)
      ON c.event_id = p.event_id
      AND c.biz_transaction_po_id = r.biz_transaction_po_id
      AND c.biz_location_join_key = ?              -- the factory location
    WHERE p.epc_rel_type = 'parentID'
      AND c.event_type = 'AssociationEvent'
      AND c.epc_rel_type = 'childEPCs'
      AND c.biz_step = 'commissioning'
  ),
  history AS (
    -- branch A: modern rows where epc_join_key is populated
    SELECT c.epc_join_key AS item_id, p.product_join_key, c.biz_transaction_po_id, c.biz_step,
           c.event_time, c.record_time, c.event_id
    FROM epc_events c USE INDEX(idx_epc_binding_history)
    JOIN candidate_items ci ON ci.item_id = c.epc_join_key
    JOIN epc_events p ON p.event_id = c.event_id AND p.epc_rel_type = 'parentID'
    WHERE c.epc_join_key <> ''
      AND c.event_type = 'AssociationEvent' AND c.epc_rel_type = 'childEPCs'
      AND c.biz_step IN ('commissioning','decommissioning')
    UNION ALL
    -- branch B: legacy rows where epc_join_key is empty string
    SELECT c.epc_id_raw AS item_id, p.product_join_key, c.biz_transaction_po_id, c.biz_step,
           c.event_time, c.record_time, c.event_id
    FROM epc_events c USE INDEX(idx_epc_binding_history)
    JOIN candidate_items ci ON ci.item_id = c.epc_id_raw
    JOIN epc_events p ON p.event_id = c.event_id AND p.epc_rel_type = 'parentID'
    WHERE c.epc_join_key = ''
      AND c.event_type = 'AssociationEvent' AND c.epc_rel_type = 'childEPCs'
      AND c.biz_step IN ('commissioning','decommissioning')
    UNION ALL
    -- branch C: legacy rows where epc_join_key is NULL
    SELECT c.epc_id_raw AS item_id, p.product_join_key, c.biz_transaction_po_id, c.biz_step,
           c.event_time, c.record_time, c.event_id
    FROM epc_events c USE INDEX(idx_epc_binding_history)
    JOIN candidate_items ci ON ci.item_id = c.epc_id_raw
    JOIN epc_events p ON p.event_id = c.event_id AND p.epc_rel_type = 'parentID'
    WHERE c.epc_join_key IS NULL
      AND c.event_type = 'AssociationEvent' AND c.epc_rel_type = 'childEPCs'
      AND c.biz_step IN ('commissioning','decommissioning')
  ),
  ranked AS (
    SELECT *, ROW_NUMBER() OVER (
      PARTITION BY item_id ORDER BY event_time DESC, record_time DESC
    ) AS rank_desc FROM history
  )
  SELECT r.biz_transaction_po_id, r.product_join_key, COUNT(r.item_id) AS qty_activated
  FROM ranked r
  JOIN requested s
    ON s.biz_transaction_po_id = r.biz_transaction_po_id
    AND s.product_join_key = r.product_join_key
  WHERE r.rank_desc = 1 AND r.biz_step = 'commissioning'
  GROUP BY r.biz_transaction_po_id, r.product_join_key
) active_items
  ON active_items.biz_transaction_po_id = po.urn
  AND active_items.product_join_key = p.id
WHERE poli.purchase_order_id IN (?)            -- same PO ids again
ORDER BY poli.purchase_order_id, p.gtin
Why LEFT JOIN for active_items? A line with zero commissioned units must still show, with qty_activated = 0. An inner join would delete exactly the lines an operator most wants to see. The COALESCE(active_items.qty_activated, 0) turns the absent row into a zero.

3. Every join, one at a time

head LEFT JOIN location

Resolves po.ship_to_location to a display name. Left, because the location is optional. Cheap: a primary-key lookup on location.

lines JOIN purchase_order

Needed to reach the PO's urn, which is the transaction key the EPC events carry (biz_transaction_po_id). The activation count is keyed on urn + product, not on the line-item id, so the line query has to climb back up to the PO to get it. It also lets the subquery and the outer query agree on exactly which POs are in play.

lines JOIN product

Two jobs at once. It supplies the product metadata for the response (name, GTIN, size, variant), and it supplies p.id as the join key on the right-hand side of active_items. That looks odd next to product_join_key, but they are the same value: the events store the product identity as /01/{gtin14}, which is exactly the product.id the line items point at. So active_items.product_join_key = p.id lines up two differently-named columns that hold the same identifier.

sub WITH requested — a CTE, not a join

Not a join, but it is the joist everything else rests on. It is the set of (PO urn, product) pairs the page actually needs. Every later step is filtered against it. This is the difference between “count activations across the whole event table” and “count activations for these POs.”

sub JOIN requested r (inside candidate_items)

Matches event rows to the products on this page. This is what stops the candidate discovery from being a full scan of epc_events.

sub JOIN epc_events c USE INDEX(…) (inside candidate_items)

The discovery step. For each parent event of a requested product, it finds the child EPC rows (childEPCs) that belong to the same event, the same PO, and the caller's factory location. The USE INDEX forces the lookup onto epc_events_biz_location_join_key_foreign so the factory fence is satisfied by an index seek rather than a scan. Note the subtlety the code comment calls out: the commissioning event must carry the factory's location, but the parent's location is not required — discovery is fenced, the full history it triggers is not.

sub JOIN candidate_items ci (inside history)

Keeps only the histories of items that survived discovery. This is the second half of the two-phase approach: phase one finds which items are interesting, cheaply; phase two fetches everything known about them. It deliberately does not re-apply the factory fence here, because a decommissioning event recorded at a different location still has to be able to cancel a commissioning event.

sub JOIN epc_events p ON … parentID (inside history)

Self-join back onto epc_events on event_id to pull the parent (parentID) row of the same AssociationEvent. The child row carries the item identity; the parent row carries the product_join_key. Doing it branch by branch keeps it inside the same index-friendly shape as the rest of history.

sub JOIN requested s (the final select)

history is built from item identities, and an item's events can mention more than one PO or product over its life. Joining back to requested at the end drops any event that does not belong to a (PO, product) pair on this page, and gives the grouping keys for the COUNT. Without it, counts could bleed across POs that happen to share an item.

4. The three UNION ALL branches

They are logically the same query written three times. The reason is entirely about index access.

The item identity is:

COALESCE(NULLIF(c.epc_join_key, ''), c.epc_id_raw)

Read that as: “use epc_join_key if it is set and not empty; otherwise fall back to epc_id_raw.” That is the right answer, but as a single expression it would have to wrap the column in a function, and that defeats the leading column of idx_epc_binding_history(epc_join_key, …). A function around a column turns an index seek into a full scan.

Splitting into three branches means each one can constrain the raw column with a plain equality:

BranchPredicateIdentity usedHits the index?
Aepc_join_key <> ''c.epc_join_keyYes — direct seek on the leading column
Bepc_join_key = ''c.epc_id_rawYes — seek on the empty-string value
Cepc_join_key IS NULLc.epc_id_rawYes — seek on the NULL range
Why not two branches? Because in SQL, = '' and <> '' are both false when the value is NULL. There is no single comparison operator that folds the NULL case into either of the other two, so NULL needs its own branch. It is not redundancy — it is the truth table.
Why UNION ALL and not UNION? The three predicates are mutually exclusive, so the row sets cannot collide. UNION ALL skips a deduplication pass that would never remove anything anyway.

5. Why the query ranks history instead of just counting

The naive query is “count the commissioning events for this PO and product.” That is wrong, and the whole shape of the subquery exists to avoid it. The quantity is the item's current state, and state can change:

item X:  commissioned 10:00  -- recorded
         decommissioned 10:01 -- no longer active
         commissioned 10:02   -- active again

Counting commissioning events gives 2. Counting commissioning minus decommissioning could go negative. The correct answer is 1: look at the item's latest event and ask if it is commissioning. That is exactly ROW_NUMBER() … ORDER BY event_time DESC, record_time DESC followed by rank_desc = 1 AND biz_step = 'commissioning'.

That is also why the history fetch is unfenced while discovery is fenced. To know an item is still commissioned you must be able to see a later decommissioning event, wherever it was recorded. Fencing the history would let a moved or off-site decommission go unseen, and the item would be counted as active when it is not.

Choosing the ordering key

event_time is the tablet's clock — the semantically correct order for an offline-first store, where a re-commission with a later event_time should beat an earlier decommission even if it synced first. record_time is the server's stamp, used only as a tiebreak, so a device with a frozen clock still gets a deterministic winner (the later-recorded event).

6. Binding mode: what the marker comments turn into

You will have noticed comments like /* declaration join */ and /* valid association event */ sitting inside SQL. They are placeholders. bindingQuery in api/binding_queries.go does a string substitution only when EVENT_TIME_BINDING_ENABLED is true; otherwise those lines stay as inert comments and the query runs in the compatibility mode above.

MarkerBecomes
/* declaration join hint *//*+ INL_JOIN(declaration) */ — a TiDB hint
/* declaration join */A LEFT JOIN epcis_events_raw keyed on CONCAT('err:', c.event_id)
/* valid association event */The has_error = FALSE checks plus a correction/deletion test against the declaration row
event_time DESC, record_time DESCevent_time DESC, BINARY event_id DESC

In binding mode the validity filter is applied before ranking, so if an event has been invalidated the winner falls back to the next valid one rather than disappearing. The two modes are the same query with a different notion of “which event is latest and real.”

7. Indexes being leaned on

IndexUsed by
idx_epc_binding_history(epc_join_key, event_type, epc_rel_type, event_time, event_id)All three history branches — the seek that makes “fetch this item's history” cheap
epc_events_biz_location_join_key_foreign(biz_location_join_key)candidate_items — the factory fence in discovery

So the query is really a two-phase funnel: an indexed seek narrows to this factory's items on these POs, then an indexed fetch pulls each of those items' complete histories, then a window function picks each item's latest event, and finally a count groups the survivors by PO and product.

Reproducing this yourself

The service has a temporary debug switch, SQL_DEBUG_LOG (default false). Set it to true and every purchase-order request logs two SQL debug lines at INFO — one for the heads query, one for the lines query — carrying the final Rebound sql and the positional args. The emitted text is exactly what go-sql-driver/mysql hands to TiDB, so you can paste it straight into a client.

SQL_DEBUG_LOG=true ./commissioning   # then hit /v1/purchase-orders and read the log

It is wired in api/sqldebug.go and called immediately before each SelectContext in GetPurchaseOrders. Off by default, so it costs nothing in production beyond a boolean check.
